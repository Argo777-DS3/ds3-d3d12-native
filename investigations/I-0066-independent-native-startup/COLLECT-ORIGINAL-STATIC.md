# The original's "collect": `FUN_140E006A0`, the scene traversal it does not contain, and what the native collect redoes (static study)

STATIC (Ghidra mirror of `DarkSoulsIII.exe` 1.15.2.0; native code at this branch, which contains main `01de1ce8`; phase A numbers from [D3D12-PHASES-A-C-PREP.md](D3D12-PHASES-A-C-PREP.md) section 8 and the retained run `evidence/I-0066/artifacts/i66-native-1276-m2`). Nothing was launched.
Status words: **STATIC** read in code or data, **INFERRED** deduced, **OPEN** not known statically. "Reviewed" marks facts first established by the independent review of this note and re-checked in the sources it cites.
Asked by the coordinator: native `collect` costs 104 ms of about 166 ms per frame in S1 (High Wall idle). The YEBIS thread published the native side ([I-0068 COLLECT-NATIVE-REPRISES.md](../I-0068-static-yebis-ffx-lights-spec/COLLECT-NATIVE-REPRISES.md)); this note is the **original side** and answers its section 5 questions Q1, Q2 and Q3 in section 5 below. It does not rewrite that file.
Evidence outside Git: `evidence/I-0066/queries/collect/`. Exports: `decompiled/DS3-1152-F-<RVA>` listed at the end. Earlier maps used: I-0067 MENUS-MAP sections 24 (layer mask, view traverser), 62 (dynamic tree, bounds, LOD, occlusion, DispGroups), 63; R8B-ENGINE-READS-STATIC (same folder).

## 0. Verdict

1. **`FUN_140E006A0` is not a collect.** It is the scene stage's per-frame update (`StageRend`, vtable `297A2C0`): about 1.3 KB of code that copies the game camera into the stage, the culler and a world-side camera record, updates the SFX and light camera, the draw-parameter transitions, the decal manager, a stage layer and the auxiliary view. **It visits no entity** (its own body and the callees read here do none; section 1 lists the callee subtrees that were not read). The native build replaced it by `UpdateNativeSceneCpu`, which reproduces those steps and **adds** the whole entity admission (`CollectNativeSelectedScene`) at its end. The 104 ms is native-only work with no counterpart in `E006A0`.
2. **The original traverses the scene per render pass scene, on the draw side.** `GXSgDrawScene` slot 0 (`FUN_1400C2EC0`) builds a traverser whose category mask comes from the engine pass id (1..4 `0x40`, 5..8 `0x02`, 9..0x38 `0x04`, `0x39` `0x10`, `0x46` `0x20`, others `0x01`) and runs the world traversal `FUN_1400C1FB0` (`GXSgWorld` vtable slot `+8` is `14004FF40`, a `JMP` to it; reviewed). The native build does **one** union walk (mask `|7`) instead of one per pass scene.
3. **Occlusion is off in the original for exactly the passes the native walk serves (reviewed).** The occlusion byte the pass scene passes to the traverser (`V+0x10`, the 5th constructor argument, `FUN_1400C2EC0` assembly lines 1-82) is 0 for pass ids 1..4, 5..8, 9..0x38, 0x3A, 0x3B..0x40 and 0x46, and forced to 0 for 0x43/0x44 and when the context count at `ctx+0x418` is above 1; it is `[GXRS+0x4E2A]` for pass `0x39` and 1 for the remaining ids. So the G-buffer, forward and shadow scenes walk **without** occlusion, as the native walk does.
4. **The original's main parallelism is across pass scenes, not across tree nodes (reviewed).** `GXSgCompositeScene` slot `+0x38` (`FUN_1402046B0`, vtable `143D4A108`), when `DAT_14473CE5B` and `DAT_14473CE59` are both set, builds **one job over all its sub-scenes** (vtable `143D61260`, the `GXDrawSceneForTask` of I-0020/I-0038), pushes it on the GX task queue `[[144961AB0]+0x2C8]` (`FUN_14020E720`) and helps drain it (`FUN_1400D1C40` wakes workers through counted semaphores, `FUN_1400D1D30`/`D1EF0` execute); otherwise it calls each sub-scene serially (`FUN_1402046B0` tests `CE5B == 0 || CE59 == 0` for the serial branch). The image values of `144473CE58..5F` are all `01`; `CE59` is recomputed each frame by `FUN_140023790` and is 1 unless `[GXRS+0x52E8]` has `+0x41B0` or `+0x4178`. **Node-level jobs** in `FUN_140208180` need `!(CE5B && CE59)` **and** `DAT_144961BC3` **and** `node+0xE0 == 0`; `144961BC3` has no recovered writer (reads only), so they are probably dead code. The native walk runs none of this: one synchronous traversal on the owner thread.
5. **What the native collect does that the original does not (INFERRED from the native code and the S1 counters; the measurement rows C-0 to C-5 split the 104 ms):** it rebuilds the whole `NativeSelectedScene` every frame and, for every admitted mesh, prepares the shader-register blocks of **every resolved recipe** for both stages and runs the texture, material and layout lookups before the programme cache is consulted, whereas the original writes per-draw values into persistent, pre-laid-out buffers for the one programme of its pass (section 5, Q2). The counters (S1: 328 visitor callbacks, 126 model intents, 1077 prepared rows, 4464 resolved recipes, 1062 native draws) do **not** give a per-mesh ratio (section 4).
6. **Proposal (section 8):** split and time the step first; cache what is a pure function of (material version, shader interface, layout) rather than whole-model admission records; produce blocks only for the rows that run; share per-frame blocks. The original's pass-scene parallelism is the model for R13's engine-side overlap but needs the GX task queue consumers, which the native build does not run.

## 2. The traversal in the original (STATIC; MENUS-MAP section 62 for the tree)

**Entry.** `FUN_1400C2EC0` (slot 0 of `GXSgDrawScene`) picks one of **two traverser classes** per frame by `DAT_14473CE5D` (reviewed): `FUN_140142A50` (vtable `143D52988`, entity slot `+0x50` = `FUN_140142E80`, with the queue and `culler vt+0x80`) when it is non-zero, else `FUN_140204C30` (vtable `143D61278`, entity slot `FUN_140204F10`, no queue); `CE5D` is written by `FUN_140D61240` ("list at `+8` empty"). The native visitor is built from the base class `FUN_140234620` and gets slot `+0x50` replaced.
`FUN_1400C1FB0(world, traverser)`: for each layer (`world+0x10..+0x18`): if the traverser's deferral getter (`vt+0x40`, which reads byte `+0x12`) and the multithreaded-rendering stub `FUN_1400BE640` allow it, allocate a task `{143D4A080, layer, traverser clone}` (the third field is `traverser vt+0x60`, a clone, `FUN_140142F90` for the collect class; the task body `FUN_1400C1D10` runs the clone: `vt+0x70`, layer `vt+8`, `vt+0x78`, then frees it), push it on the GX queue (`FUN_14020E720`, two locks), set `[144961AB0]+0x2F9` and the wake flag `DAT_144961BC7` when `[lower+0x328]`; otherwise call the layer's `vt+8` at once. The scheduling bytes: `+0x10` occlusion (`vt+0x28`), `+0x11` parallel nodes (`vt+0x38`, set from `passctx+0x424`), `+0x12` deferral (`vt+0x40`, set by `C2EC0` to `CE5A && CE59` and the pass not being in 9..0x38). `FUN_1400BE640` gates only layer deferral.
**Layers.** `GXSgLayerFlat` (`FUN_1400C2630`): layer mask `+0x30/+0x34`, per item `(item+0x20).lo & t.lo` and `.hi & t.hi`. `GXSgLayerDynamicTree` (`[[144796298]+0x10]+0x50`): characters only (two inserters, `FUN_1408853C0`, `FUN_1408B76A0`). Which layers hold map objects is **OPEN** (MENUS-MAP section 62 subsection 5).
**Nodes (`FUN_140208180`).** Per node: skip when empty (`+0xE4` and the entity list); **subtree mask** `node+0xD8/+0xDC`; optional occlusion (cell visible-until `+0x44` against frame `+0x160`, state `+0x78`); frustum on the loose bounds `+0xA0`; children sequentially or as node jobs (conditions in verdict 4); the node's own entities: mask `+0xD0/+0xD4`, frustum on `+0x80`, per entity `(E+0x20)` masks, then the traverser's entity method.
**Entity method of the collect class** (`FUN_140142E80`): skip on the occlusion node state, frustum-test the entity's `vt+0x18` bounds (`E+0xB80` for `SprjModelDrawEntity`, `E+0x40` for `SprjModelDispEntity`) unless the parent was fully inside, call `culler vt+0x80` (its result goes to `ctx+0x4EC`), then the entity's draw slot directly or queued.

**Caches and incremental structures kept across frames (STATIC):**
- the tree: nodes move only when an entity's bounds change (`FUN_14002D800` -> `FUN_140207B40`, from the draw-entity update path `FUN_140C4AF10` -> `FUN_140D07710` -> `FUN_140D08190`, which recomputes `E+0xB80` only when `BA8` bit 2 is set);
- the subtree masks and node bounds, maintained on insertion and move;
- the occlusion cell and node states (`FUN_1400CA050`), refreshed from the previous frame's queries (used only by the passes that enable occlusion);
- the LOD controllers per entity (`E+0xB0`, `E+0x150`), advanced once per frame by the `0x4F/0x50` tasks, holding the distance fade weights;
- the per-entity visibility words (`D03430`, `D03050`) and the current DispGroups (`[E+0x70]+8..+0x27`, `FUN_140621730` once per frame).

## 5. Answers to the YEBIS questions (section 5 of COLLECT-NATIVE-REPRISES)

**Q1. How many draws and constant uploads does the original's emit produce per frame at S1?** *Draws:* the original's draw count per pass is the number of rows its recorder executes (`FUN_140057A20` dispatches the rows to `FUN_14005C0E0`/`FUN_14005C060`, 12 and 8 call sites; the native row logic is a transcription of these rows). The native main-view draws (G-buffer, forward and velocity rows) are **1062 per frame** in S1 (`content_draws`; 1077 prepared rows, 15 not drawn); the original draws the **same rows plus those of the passes the native build does not run** (shadow-map pass scenes 1..4 per cascade or light, other views); that total is not countable statically because the number of pass scenes per frame is OPEN (row C-6). *Constant uploads per draw (STATIC structure):* each draw runs the material apply `FUN_140140850` (one material-constant block rewritten by `FUN_14022D620`/`FUN_14022E930` and uploaded by `FUN_14002E5C0`), the VS model-param builder (`FUN_14005B3D0`/`FUN_140059470`, uploads through the GX update functions `FUN_141920300/660/9D0/E20`) and the PS model-param builder (`FUN_1401A86C0`, same functions), plus per model the pose palette and per fade the instance record, plus per pass the scene, view and light blocks. That is **at least three constant writes per draw**, i.e. about 3,200 per frame for the 1062 main-view draws, and more with the other passes (INFERRED; the exact count is row C-6: count calls of `14002E5C0`, `140059470`, `1401A86C0`, `14005B3D0`, `140057A20` and `14005C0E0` per frame in a Reference run).
**Q2. Does the original cache per-material constants?** *The buffers are persistent, the values are not cached (STATIC at the call site).* `FUN_140140850` indexes a per-material table `param_1[0x13] + [[ctx+8]+0x2200] * 0x28` (a record per context index, created once with the material, "creation zero" in MENUS-MAP sections 66 and 67) and calls `FUN_14022D620(material+0xD0.., record, parameter animations, name, pass, draw state)` **on every draw**; `FUN_14022D620` iterates the material's parameter records (stride 0x90), builds the blended copy (`FUN_14022E0F0`, `FUN_14022E5C0`) and `FUN_14022E930` writes the values into the pre-laid-out record; then the record is uploaded. No dirty or version gate was found at that call site (gates inside `22E0F0/22E5C0` were not read). So the original recomputes the **values** per draw but does **no layout analysis**: the position of every constant in the buffer is fixed when the material is created. The native `PrepareReadShaderRegister` per mesh, recipe and stage does the layout work (which words the shader reads, ranges) again each frame; that layout result is a pure function of (shader interface, reads, declaration) and is what a native cache can hold.
**Q3. What are the ~12 ms outside the three phases?** The frame time is the pacing window (`120 / wall`); the three phases are collect (the bracket in `UpdateNativeSceneCpu`), prepare (`PrepareNativeModelFrame` in `Clear()`) and render (`RenderNative*` and `Present` in `Clear()`, `:625-641`). Everything else on the owner thread is outside: (a) **the engine's own CPU frame**, all FD4 steps `0x00` to `0x4F` (game flow, menus, Havok world update, ChrIns updates, cloth, AI, sound, network, the Scaleform CPU update) and the draw-side steps other than the two native hooks; (b) the native hooks outside the brackets: `FrameBegin` (`:6113`), the body of `NativeRenderStep` (`:7236`: sampler settings, quality object, **the UI CPU frame** `session->PrepareFrame`, which is not one of the five UI admission phases), the `EndFrame` prelude (`:7318`: clock preservation) and `Clear()`'s start (`AcquireNativeSelectedScene`, `PublishNativeSceneCopy`, `:617-624`) and tail (the pacing row, `ProbeWorldUpdateHooks`); (c) the non-collect part of `UpdateNativeSceneCpu` (the `E006A0` equivalent, small by section 1). The static reading cannot split them; **row C-0b** adds timers for FrameBegin to `UpdateNativeSceneCpu` entry (engine update), `NativeRenderStep`, and `EndFrame` to `Clear()` entry.

## 8. Proposal (original-derived; native detail belongs to the YEBIS file)

1. **Measure first (rows C-0, C-0b, C-1 to C-5).** Log the admitted-mesh count; split the bracket into traversal alone (`:4697`), `AdmitNativeSelectedObject` self time, the per-mesh pre-cache lookups (N3, N4), the recipe x stage loop (N5), `PrepareNativeSelectedPasses` and the light collectors.
2. **Cache what is a pure function, not whole-model records.** The original's design is "layout fixed at creation, values per draw". The native equivalent: cache per (shader interface, declaration) the **layout result** of `PrepareReadShaderRegister` (ranges to fill), per (material version) the numeric parameter words and the texture bindings per registry version, and per layout the programme lookup chain of N3; recompute only values. This is safe because those inputs do not depend on the frame. **Do not reuse whole `NativeSelectedModel` records across frames** (reviewed): they carry per-frame data (`scene_blocks`, `view_blocks`, `instance_blocks`, pose and previous pose, stream and cloth generations, texture residency with the `_l`/`_atlas000` fallback) that no engine signal covers.
3. **Engine change signals are a later layer, with their gaps (reviewed).** The dirty push `FUN_140C4AF10` and `FUN_14002D800` serve the draw-entity path; the map-piece items (`SprjFD4ModelItem`, about 174 per frame in S1) update through `FUN_140D3E950`; `FUN_140D1CCE0` (LOD) and `FUN_140621730` (DispGroups) rewrite values every frame, so they are writers, not signals; the `+0x180/+0x181` dirty bytes are set by `FUN_140D254B0` and the render-side emit but no clearer is cited, so natively the byte may never reset. R8B-ENGINE-READS-STATIC leaves the fade (`+0xDC`), wet and appearance writers untraced. A version-stamp scheme (C4-C7 of the YEBIS file) needs R8B-1 and R8B-3 evidence first.
4. **Produce blocks only for the rows that run, and share per-frame blocks**: the row set is known from `PrepareNativeSelectedPasses`; the scene and view ranges are built once per (recipe, stage) and prepared per distinct interface.
5. **Parallelism.** The original's default is pass-scene tasks on workers. Enabling `visitor.base[0x11]` (node jobs) would do nothing here: `DAT_144961BC3` has no writer and the jobs go to the GX task queue that the native build does not consume. A native job queue, with the traversal split over layers or pass scenes, is the R13 engine-side work; it is not a flag.
6. **Occlusion** is not a difference for the G-buffer, forward and shadow scenes (verdict 3); it concerns pass `0x39` and the other ids only.
