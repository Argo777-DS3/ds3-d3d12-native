## 0. Answer first

1. **The configuration has 18 keys (15 settings counting the four resolution keys as one) plus the brightness option; 11 keyed settings and one unkeyed slot (the decal byte, fixed at level 3) feed one 0x78-byte "quality object" through a 0x24C-byte table** (MENUS-MAP 77). Native builds that object since Native1255 and rewrites it when a level changes, but **only one native consumer reads the object itself: the point-light fade (`+0x40`, Lighting)**. Two other native consumers read the **levels** directly from the config block, each with its own validation: the sampler bank (Texture, `settings+0xA8`, double read) and the velocity gate (MotionBlur, `[image+0x4796298]+0xB8`, single read, with its own copy of the table obtained by calling `219B0`). The other options have no native consumer yet.
2. **Only two options have a native effect today, and neither recreates a resource or a pipeline:** Texture quality selects new sampler descriptors (new entries in the content-keyed global sampler heap, capacity 128 tables; a full cache falls back to per-draw tables); MotionBlur toggles the velocity rows (the velocity targets and pipeline are created on first use and then kept).
3. **Mismatches between an option and native behaviour (section 3):** **ShadeQuality** gates the skin SSS stage in the original (`+0x75`), but native builds the SSS stage whenever the profiles exist; **brightness** is computed into `native_colour_settings` but no gamma pass applies it; **ScreenMode and resolution have no effect natively** (STATIC): the Options-page request is queued on a GX object that does not exist natively, and the window's own size changes are not followed (swap chain and `output_width` stay at the start size, the picture is stretched by DXGI, INFERRED); **Antialiasing** `ON` is level 3 in the block and sets byte `+0x08`, which no native pass reads.
4. **What recreates what (section 4), when the families exist:** class P parameters only (Lighting, Effects values, Texture samplers); class G gates (a pass appears or disappears: SSAO from LOW, DoF, MotionBlur, Antialiasing, Reflection, Water, Shade, decals), which change the **plan structure key** of the phase E sheet, create resources and PSOs on first enable, and, when they add transients, change the placement plan (section 4); class R true recreation behind a ring-wide `WaitIdle` (ShadowQuality's atlas, which also depends on the zone's ShadowParam class, the reflection target divisor, and the display keys once wired); class H history resets (SSAO's temporal variants, motion blur, resolution).
5. **One mechanism, not twelve (section 4):** an `OptionChange` evaluated once per frame on the owner thread **on the same comparison `UpdateNativeQualityObject` already makes with the applied copy `root+0x52F0`**, whose result is a value in the frame input; it replaces the three independent direct reads of the levels.
6. **Phase G's API options (part B):** none is justified by a measurement yet; the later sheets change two conditions (root CBVs; enhanced barriers).
7. **Next sheet proposal: section 8** (persisted there).

## PART A. The game's graphics options

## 1. The options and the path to the engine (STATIC)

- **File and tokens:** `GraphicsConfig.xml`, writer `FUN_140EF75A0`, reader `FUN_140EF8430`; keys in order: `ScreenMode`, `Resolution-WindowScreenWidth/Height`, `Resolution-FullScreenWidth/Height`, `Auto-detectBestRenderingSettings`, `QualitySetting`, `TextureQuality`, `Antialiasing`, `SSAO`, `DepthOfField`, `MotionBlur`, `ShadowQuality`, `LightingQuality`, `EffectsQuality`, `ReflectionQuality`, `WaterSurfaceQuality`, `ShadeQuality`. Tokens: quality keys `DISABLE`, `LOW`, `MEDIUM`, `HIGH`, `MAX`, `CUSTOM` (0 to 5); `Auto-detect` and `Antialiasing` `ON`/`OFF`; `ScreenMode` `WINDOW`/`FULLSCREEN`. The reader keeps a field's previous value for an unknown token (MENUS-MAP 77.1).
- **Levels to the object:** `image+0x4796298` holds a pointer to the settings owner; the twelve `int` levels are at `[image+0x4796298]+0xA8 + 4*slot` (block `+0x08`); `D55190 -> DFDD20 -> CED9A0 -> 23660` copy them to `GXRS+0x5320..0x534C`; `FUN_140023790` rewrites the quality object `[GXRS+0x5360]` from the table `[GXRS+0x5358]` when a level differs from the applied copy `GXRS+0x52F0..` (MENUS-MAP 77.2; QUALITY-OBJECT-NATIVE). **The presets do not recompute the levels at load**: with `QualitySetting=LOW` in the file the block still holds the per-key values (QL3, Native1263).
- **Native reads of the levels (three, independent):** (a) `UpdateNativeQualityObject(settings)` (`:4895-4913`): twelve levels read twice, each 0..4, written to the object only when a level differs from the applied copy; run every render step on the owner thread (`:7927`); (b) `RefreshNativeSamplerSettings(settings)` (`:4915-4930`): reads `settings+0xA8` twice, publishes the sampler selector; called from the render step (`:7926`), from the collect (`:5188`) and from the offscreen collect (`:6989`, which can run inside `Clear()`, phase F sheet section 1); (c) `NativeMotionBlurQualityRow` (`:5104-5109`): one read of `[image+0x4796298]+0xB8`, then its own static copy of the table obtained by calling `219B0`. The object is published at root construction from the initial levels (2, then 3 x 11; `:9865-9877`).

## 4. What an option change recreates, by class (design for when the families land)

| Class | Meaning | Options | On change | Phase D/E/F interaction |
|---|---|---|---|---|
| **P** parameters | values only | Lighting float, Effects values, Texture (new sampler tables), Brightness (curve texture contents) | none beyond the object rewrite; the bank generation changes the prepare cache keys | none |
| **G** gates | a pass appears or disappears; resources and PSOs on first enable | SSAO (DISABLE to LOW and above), DoF, MotionBlur, Antialiasing, Reflection, Water, Shade, the Effects flag bytes, probably part of Lighting | **the plan structure key changes** (phase E sheet 5.1); resources created on first enable (kept), PSOs prewarmed (below); **if the gate adds transient targets the placement plan changes**: either size the placement once for the **union of the transients of all gates** (recommended: toggling an option then changes only the plan key and the barriers) or treat "G with transients" as a placement generation (new heap, old one kept by `RetireAfter`/`WaitIdle`, phase D L4) | the plan is recompiled once |
| **R** recreation | an existing resource has a different size or count | ShadowQuality (atlas size) and the zone's ShadowParam class, the reflection divisor, ScreenMode and every Resolution key once wired | ring-wide `WaitIdle`, release by ticket, recreate from the new size, reset histories | phase D `WaitIdle` and retirement; phase E placed heaps recomputed; `ResizeBuffers` with every back-buffer reference released |
| **H** history reset | temporal data invalid | SSAO at the temporal boundary (MEDIUM to HIGH) and on enable, MotionBlur enable, resolution, (DoF/AA with their histories) | R-T1/R-T2 of the phase D complement: the reset travels with the frame | same |

**The mechanism (proposed).** `OptionChange` is evaluated once per frame at frame start on the owner thread: it **builds on the comparison `UpdateNativeQualityObject` already makes** with the applied copy (`root+0x52F0`) rather than adding a second one; (1) it reads the twelve levels, the brightness and the display keys **once**; (2) classifies the delta with the table above; (3) applies R, then G, then P, then H in one place; (4) logs one row (`native_option_change`: levels, class, resources created/released, PSOs created, `WaitIdle` time) so the cost of an option change is measured; (5) the **snapshot of levels is a field of the frame input** (a value), so `RefreshNativeSamplerSettings`, `CollectNativeVelocityInputs` and the render thread (phase F) read the snapshot instead of the live block; the phase F census is extended with `native_sampler_bank`, the object and applied copy at `root+0x5360/0x52F0`, and the velocity function-static table (routing note, section 9).

**First-use hitches.** Enabling an option that adds PSOs would compile them on the frame path (the first lit frame already does, complement 4.2). R9 C1c (creation off the draw-cache lock) covers model PSOs only; the AO, AA, DoF/YEBIS, gamma, SSS and reflection PSOs belong to `SceneRenderer`. The simplest policy is to **prewarm the fixed set at startup, independently of the options** (about 45 PSOs for the planned families, INFERRED from the family notes; AO 7 plus on-demand variants, SSS 2, AA 1 to 2, YEBIS/DoF about 30), which removes the need to read an option ahead of its use and any one-frame delay of the gate.

## 5. Gates that are not quality levels (do not mistake them for options)

Light shafts, colour grading, LUT, exposure, shadow variant: zone Setting Info and gparams (master plan S5, YEBIS checklist); glare and glow: option factors `[[GXRS+0x5368]+0x68/+0x80]` (1.0 unless an options rewrite changes it); AA also needs the factor `[[GXRS+0x5368]+0x98] > 0`. These do not appear in `GraphicsConfig.xml` and do not change with the Options page.

## PART B. Phase G API options (master plan 2.9, 2.10), updated

## 7a. Amendment 2026-10-31: « Auto-detect best rendering settings » (study thread, at Thomas's request; static, GhidraMCP)

The in-game help says the option sets « whether to simplify rendering in the case of reduced performance ». What the original's
plain code shows:

- **Storage.**
  - The XML reader `FUN_140EF8430` writes ScreenMode to `config[4]`, Auto-detect to **`config[5]` (byte offset `+0x14`, `ON`
    1 / `OFF` 0)** and QualitySetting to `config[6]`.
  - The config is embedded at `owner+0x68`: the writer wrapper `FUN_140EF5AB0` calls `FUN_140EF75A0(owner+0x68, ...)`, and
    the window path `FUN_140EF54A0` reads ScreenMode at `owner+0x78`.
  - The owner is the global **`[14489F118]`**, loaded by the start-up `FUN_140EDB220` before the call at `140EDC33A`. So
    Auto-detect is **`[14489F118]+0x7C`**.
- **Readers.**
  - Of the 79 loads of `[14489F118]` in plain code, one touches `+0x7C`: `FUN_14059FB70`, which copies the settings into the
    Options page's data model (`model+0x63 = (Auto-detect == 1)`, `+0x64` the preset, then the per-key levels).
  - No other plain-code access to `+0x7C` was found, in a scan of the window and config code `140ED0000..140F00000` included.
  - The level path that feeds the GX quality object (`SprjDrawStep+0xA0` → `140CED9A0` → `140023660` → `140023790`) does not
    read it, and the quality object has no field for it. `140023660` copies the levels unless the lock byte `GXRS+0x5350` is
    set, which no plain code sets (0 in QUALITY-OBJECT-NATIVE-LIVE).
- **So** whatever the option does is in encrypted code: either the Options page itself (the encrypted page that applies the
  presets, MENUS-MAP 77.5), or an encrypted runtime monitor that would rewrite the levels under load. Static reading cannot
  tell which. The string `FD4PerformanceManager` (`143D7CF60`, next to a table of empty or undisassembled stubs `140354xxx`)
  is the only performance-manager name in the executable; no link to the option was found.
- **Native today.** The option has no reader of its own (no `Auto` in `native/`). But `UpdateNativeQualityObject` reads the
  twelve levels every render step, so **if the original's encrypted code lowers the levels at run time, native already
  follows** for its existing consumers: the point-light fade, the sampler bank and the velocity rows.
- **What would decide it** (an original run, announced, offline; not a native change):
  - Auto-detect ON, a heavy scene (FPS well under the cap), the twelve levels of the block and the quality object logged once
    a second (the existing `native_quality_object` style row on the Reference side).
  - If the levels drop at run time while the menu is closed, it is a dynamic simplification, and the row gives its threshold
    and steps.
  - If they change only when the box is ticked in the menu, it is a one-time « detect » that writes a preset, nothing at run
    time.
  - A cheaper first look: tick the option in the menu and diff `GraphicsConfig.xml` before and after.
- **Live results (2026-10-31, Thomas's yes of 09:30 Paris):**
  - **Thomas's diff** (the original, the Options page): ticking the option changed only `Auto-detectBestRenderingSettings`
    (OFF to ON). `QualitySetting` stayed `CUSTOM` and the ten quality keys were unchanged, so it is **not a one-time detect
    that writes a preset**. The screen-mode and window lines in the same diff came from another pilot's run, which had
    edited the file while the « before » copy was taken.
  - **Run `study-autodetect-ref`** (Reference, the Firelink replay with Eta, 11:10-11:17 Paris): Auto-detect ON, every quality
    key at MAX, a 1920x1080 window, configuration and save restored by hash.
    - A read-only poller (`Watch-AutoDetect.ps1`, on the study branch) read 384 samples, one a second: the option
      `[14489F118]+0x7C`, the block `[[image+0x4796298]+0xA8..]`, the GX copy `GXRS+0x5320..`, the applied copy
      `GXRS+0x52F0..` and the dt.
    - The option read 1 throughout. **No level ever changed**: block = GX copy = applied = 4,3,4,4,4,4,4,4,3,4,4,4 once

    - The poll is in `evidence/I-0066/artifacts/study-autodetect/`, the run in `.../study-autodetect-ref/`.
  - **So**: the option rewrites nothing when ticked and lowers nothing at 60 frames/s. What it does under a real loss of

    original's encrypted code lower the levels, `UpdateNativeQualityObject` already follows them every render step.
  - **Decision (Thomas, 2026-10-31 12:39-12:40 Paris)**: the option stays as it is for now. In the rework of the menus
