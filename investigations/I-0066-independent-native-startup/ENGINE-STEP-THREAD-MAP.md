# Which FD4 step and which thread: the engine's frame timeline, its thread pool, and where each native hook runs (static study with the runtime logs already on disk)

Request (coordinator, 2026-10-11 18:29 UTC, proposition 2): find the FD4 step and the thread of the collect, of the stream, cloth and pose hooks and of the retirement hooks; answer R8B-2 and the open thread points of [phase F](D3D12-PHASE-F-SHARED-STATE-SHEET.md); unblock F2. Nothing was built, run or measured for this note. It reads the Ghidra mirror (read-only queries) **and the thread ids and call stacks that the native module already wrote into the retained runs**. An independent Opus 5.5 pass found that the first version read the row table 0x10 bytes late; this version is rebuilt on the corrected table.

Grades: **OBSERVED** (a retained runtime log shows it), **STATIC** (code or data read in the mirror), **INFERRED** (a consequence of the previous two, with its reason), **OPEN**.

## 0. Answer first

1. **The frame is a table of 88 rows, each with six lanes** (STATIC, 88 six-`int` records from `.rdata 1429BB1A0`, read by `FUN_140F0FF50`; 97 step records `{id, name, group}` from `1429BA580`, ids 0x00 to 0x60). Lane 0 holds the serial steps: 81 of the 97 steps are group `g1` and appear in lane 0 only (step 0x01 `FD4TaskMng` is outside the table). Lane 1 holds the four `g2` steps (`FileStep` and the three Scaleform steps), lane 2 the two `g4` silhouette steps, lanes 1 to 3 `UpdateLodIns` (`g14`), lanes 1 to 5 `HavokBehavior_SceneModifier` (`g62`); five `g63` steps (`ChrIns_PreBehavior`, `_PrePhysics`, `_PreCloth`, `_PostPhysics`, `HavokClothUpdate_Pre_ClothModelIns`) fill all six lanes of one row, `ChrIns_UpdateDraw` fills lanes 0 to 3 and `_UpdateDraw_End` lane 0. **The group is a bit set over the lanes: bit i = lane i.** It matches the table for 97 of 97 steps. That this is the engine's rule ("group = the lanes the step may use") is consistent with the data; the consumer of the group was not read.
2. **Lane 0 is the thread that calls the task manager.** The manager's run function binds six lane jobs to six worker slots; slot 0 is not signalled and is run by the caller (STATIC, `FUN_1423757D0`, `FUN_142393830`). Six `FD4JobWorker:N` threads exist (`FUN_14234CDD0`), so slot 0's own thread is created but idle. A captured call stack of a `MoveMapStep` call (a `g1` step) bottoms at the C runtime entry and passes through the manager run (OBSERVED, 1,494 captured calls, none on a pool thread).
3. **The collect runs in the `DrawStep` row, on the caller thread, with every other lane empty.** `E006A0` is reached from `FUN_140D54F80`, a `DrawStep`-family method (INFERRED: same code region, same `RendMan` global `[144796298]` and same profiler as the render step `D55190`; its only reference is `.pdata`, so its caller is undisassembled code). `DrawStep` is `g1`, **row 79, alone in its row**. The render step, `BeginFrame` and `EndFrame` refuse any other thread than the owner thread and have not refused in the retained runs (OBSERVED, except one refusal during shutdown in `i66-native-startup-23`), and the owner thread is the window thread in 506 of 506 runs (OBSERVED). So the collect and the prepare run on the owner thread in one frame (INFERRED, strongly: the three reasons above and the K stamps, section 3). **R8B-2 is answered, not closed:** the row stays "INFERRED" until TM-3 (one captured stack) is run.
4. **The model and UI tasks run on the owner thread and on pool threads.** The player-model update reached through the `ChrIns` Ez tasks (`g63` steps) ran on the owner side in 68 % and on a pool thread in 32 % of the periodic samples (2,082 against 991; OBSERVED); the same update reached directly from `MoveMapStep` ran on the main thread each time (1,494 of 1,494). The Scaleform UI session was created on a pool thread in 472 of 475 runs (OBSERVED; the 3 exceptions are the first three runs). Which lane a given character's task is assigned to is not read.
5. **For F2:** the update rows (0 to 78) run on up to six threads and write the model state that prepare reads (the `ChrIns_*` steps are `g63`); R8b S1 to S4 must therefore snapshot at collect (confirmed). A prepare that runs on the render worker overlaps (a) the **rest of the same frame's rows 80 to 87** after `EndFrame` returns (`DrawBegin`, `GameSceneDraw`, `AdhocDraw`, `DrawEnd`, `Flip`, **`DelayDeleteStep`**, `RecordHeapStats`, `FrameEnd`: this is the retirement path of section 4) and (b) the next frame's update rows. Threads outside the task table also exist (section 3): seven `GXWorker`, a `HavokWorkerThread`, the loaders. Details in sections 5 and 6.
6. **Still OPEN:** the step of the `*ModelIns` task (map-item wind block `E4`/`E6`), the exact thread of model-storage admission and retirement, of pose creation and retirement, of the vertex-stream patch, of Bink and of the cloth upload, and the step of every Ez task other than the `ChrIns` ones (the registration function `FUN_14065CAC0` is undisassembled).

## 2. The frame timeline (STATIC)

**Where it is built.** `FUN_140F0F5B0` (called from `FUN_140EDB220`, the game's one-time set-up) creates the singleton task manager `[14489F350]` (`FUN_140F0FD50`, 0x61 step objects). For each record `r` the step in column `j` gets the mask `1<<j` for row `r` (`FUN_140F121D0`) and is wrapped in a `SprjTimeLineTaskGroupIns` (`FUN_140F10800`). ## 3. The threads and the runtime evidence

**The pool (STATIC).** `FUN_14234CDD0` (called by `FUN_14234D090` inside `FUN_140F0F5B0`) builds the job system: `FUN_142393AA0` creates six worker wrappers (`FUN_1423C5990`), each started by `FUN_1423C5A20(worker, index, priority)` for index 0 to 5 with no test on the index; the thread is named `FD4JobWorker:%d` (format at `143D36340`, stack 0x20000, `SetThreadPriority` from the configuration) and runs `FUN_1423C5840` (wait on its event, drain its queue). In `FUN_1423757D0` the six lane jobs are bound to the six worker slots; **slots 1 to 5 are signalled, slot 0 is not**: the calling thread runs it through `FUN_142393830`. So lane j is worker j, and lane 0 is the caller (the call to `FUN_1423C5710` in that function is dead code of the decompiler). Not read: the code that makes a step run on its lane's job (the consumer of the step records' group); the mapping is consistent with all 97 steps and with the stacks below.

**Other threads, outside the task table (STATIC, names only; the owners are not read):** `GXWorker 1` to `GXWorker 7` (`.data 144731B90..BC0`, strings at `143D1B310..`), `GXWorker:%d` (`143D4BE00`), `GXWorkerThread%u` (`1429597C8`), `IGXWorkerThreadCallback`/`GXWorkerThread@Tasks@GXBS` (RTTI), `HavokWorkerThread` (`142A65488`), the loaders and file threads. The cloth upload takes a context from a pool of **7** (`FUN_1423A0130`), which matches the seven `GXWorker`s (hypothesis, not read).

## 5. What this answers, and what it changes

1. **R8B-2.** Answered with INFERRED status: the collect, the render step, `EndFrame` and `Clear` are consecutive on the owner thread inside one `DrawStep` step, so the scene produced at collect is the one `Clear` consumes. What would close it is one captured stack at each frame hook (TM-3). The "thread not established" statements of [R8B-ENGINE-READS-STATIC](R8B-ENGINE-READS-STATIC.md) section 3 become "pool-capable" for the writers of the character group state (fade, wet, appearance, wind): they run in the `g63` steps, before the draw rows.
2. **Phase F.** "Owner thread = window thread, INFERRED" is OBSERVED (506 of 506). That this is also the thread that runs the task manager's lane 0 is OBSERVED for the manager (stack) and INFERRED for the identity. The F sheet's thread table gains the pool threads (`FD4JobWorker`, up to five working) **and** the threads outside the task table (`GXWorker`, `HavokWorkerThread`, loaders) as callers of the model, pose, stream, UI and storage hooks; the locks it lists are already taken by them.
3. **F2 / R13 cR5.** (a) Snapshots at collect remain required: the `g63` steps rewrite the model state on up to six threads in rows 23 to 57, before the collect. (b) Once `EndFrame` returns, a prepare on the render worker overlaps **rows 80 to 87 of the same frame** (including `DelayDeleteStep`, the engine's delayed deletion, and `Flip`) and the **update rows of the next frame**; any engine object read from the worker is a race with those. The R13 sheet's rule "no engine read on the worker" stands and the retirement hooks must not free anything the worker still holds (the F sheet's kept-set rule). (c) Whether the pool and the other worker threads are quiet during the `DrawStep` row is not shown: the lanes are empty, but the `GXWorker`, Havok and loader threads are outside the table. The collect must not assume exclusivity against them; the K parallel scene pool, if designed, uses its own threads.
4. **cF.5 allow-list** (`Test-ThreadAffinity.ps1`): the owner-only list is `Start`, `BeginFrame`, `UpdateNativeSceneCpu`, `NativeRenderStep`, `EndFrame`, `Clear`, `Post`/`Quiesce` and what they reach on the renderer; every other hook of section 4 is "pool-capable or unknown" until TM-1 narrows it.
