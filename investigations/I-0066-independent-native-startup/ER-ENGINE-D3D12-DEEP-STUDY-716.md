## What is established

The recovered method has current engine owners create native resources, current CPU writers record native updates, current model/view/instance/material selection choose those resources, and the current context emit native bindings and draws. Submission retires upload allocations against the actual queue fence. These are responsibilities within the integrated renderer, using its shared device and context services. The selected path does not serialize current data through Capture/Join, a virtual file, or a second rendering host.

This study closes considerably earlier inputs than report710. In particular, the exact RTTI-named **CSFgModelVertexStreamPatch** has a real CPU writer, native allocation/update, selected-draw override, and destruction path. It is not inferred from a target factory. The normal **GXFlverModelRendererDrawImplDefault** chain independently joins current LOD/mesh/primitive selection to IA bindings and DrawIndexedInstanced. A material collector joins actual current CPU parameter bytes to upload storage, a native CBV, and root-table preparation.

| Requested chain | Static result | Remaining boundary |
|---|---|---|
| Current model/view/instance/material → selected primitive | Closed from current renderer arguments, LOD/masks and current material resolver through admitted mesh/primitive | World visibility construction, all caller families and all material algorithms are not reconstructed |
| Selected vertex/index → native IA/draw | Closed for ordinary indexed default Flver draw, including current patch override | Other renderer implementations and special draw branches are not qualified |
| Dynamic CPU geometry → allocation/update → selected binding | Closed nominal CSFg patch path with exact vtable identity | CPU simulation that fills the source arrays, every failure branch, and same-live-instance identity are not qualified |
| Current material constants → native storage/descriptors | Closed animation collector and actual CPU-byte CBV path | All texture producers, shader semantics and all material families are not reconstructed |
| Upload lifetime → native completion | Closed submission token, deferred block and GetCompletedValue comparison | Default-resource delayed release uses another policy; see below |
| Ordered recording/submission/presentation | Native execution and presentation each established; CPU worker processes its recording queue before its presentation callback | Concrete registration joining the recovered presentation callback to that worker's virtual callback remains unresolved; no single live draw-to-present witness |

## 1. Current engine selection reaches IA and draw

`primitive/01AAA100` takes the current renderer/model/context arguments, requires model readiness, clamps current LOD, uses the current matrix provider (`141A92820`), invokes the current context callback, and chooses the current material/instance set from an override or the model. It enters `flver-draw/01AAB2F0` with those associations. The latter adjusts the requested LOD against the model's available-LOD mask, consumes current view masks and current geometry/material tables, and visits model mesh records. A current material resolver is called with the mesh's material ID; masks and current material state/variant gates decide admission. Scoped current callbacks surround processing. This is selected current work, not enumeration of every loaded native asset.

`primitive/01AAC2B0` selects `param_8[param_9]`, the current per-instance record. The indexed arm obtains the current primitive through the mesh/group index tables and model primitive records (0x40-byte records at model+0x260). It obtains the current index resource through primitive+0x38/+8, sets context+0x270/+0x278/+0x27C, and calls `141E8DA60`. It next calls `141AAAE90` with the current model/mesh/primitive bundle, context and instance record, applies current topology/fixed state, then invokes renderer+8 virtual slot0 with the current primitive and base-vertex arguments. Exact RTTI/vtable `142F1EF78` identifies default slot0 as **141C400A0**; `model-vtable-scan/decomp/01AA9000` stores the incoming draw implementation at renderer+8. This proves the default implementation selection, not that every live renderer always uses it.

`vertex-selection/01AAAE90` follows the selected mesh's stream-index table at +0x38 into model geometry records at +0x288, stride0xA0. Each current geometry supplies native resource+0x70, stride+0x68 and byte offset+0x78, optionally adjusted by base vertex+0x6C. If instance record+8 contains a stream patch, it calls that patch's virtual+8 with the current stream index, offset, instance index, geometry, mesh and current associated primitive/material argument. Otherwise it directly selects original current geometry. A patch returning false also selects original geometry. These are two native-resource choices within ER; they are not an old-API fallback strategy for DS3.

`ia/01E8DAF0` builds actual D3D12_VERTEX_BUFFER_VIEW values from native resource at wrapper+0x20, GetGPUVirtualAddress (resource slot0x58), requested offset, remaining byte size and stride. It calls command-list **slot0x160 IASetVertexBuffers**. `patch/01E8DA60` similarly builds D3D12_INDEX_BUFFER_VIEW and calls **slot0x158 IASetIndexBuffer**. Slot0x168, encountered during exploration, is stream-output binding and must not be mislabeled IA.

Report710's `entry/01C400A0.asm.txt` actually tail-jumps at `141C400CF` to `141ACAF20`; `ia/01ACAF20` runs current preparation `1419E3700`, dirty descriptor preparation `141ACD170`, then `141E8E0D0`. The latter emits **DrawIndexedInstanced, command-list slot0x68**, with current index count/start and base vertex, instance count1/start instance0. Current mesh selection, binding and command construction are thus connected through actual call/virtual targets.

## 2. A genuine dynamic-stream owner and CPU writer

PE-backed RTTI establishes `CSFgModelVertexStreamPatch` vtable **1429D16C8**: destructor `1401E9290`, selected binding `140B75270`, resource callback `140B75350`, and update `1401E92F0`. Base and `CSFD4ModelVertexStreamPatch` identities are separately recorded; they must not be conflated.

`native-update/001E7160` creates the CPU owner with current upstream objects, allocates arrays (two 12-byte-per-element arrays at +0x28/+0x30 and a 4-byte-per-element array at +0x38), constructs a 0x40-byte CSFg patch with actual model/mapping/owner arguments, retains it at owner+0x40, and calls `140B74FB0`. `vtable-scan/decomp/001E9230` stores mapping+0x30 and CPU owner+0x38 after the base constructor; `00B74D60` establishes model+8 and initially empty native-buffer/view/map arrays and ready flag.

`update/00B74FB0` first withdraws old associations through `140B74E50`. It allocates buffer/view/mapping arrays from the real model's geometry count, initializes invalid maps to -1, asks the concrete patch's mapping virtual for admissible geometry, and derives byte count from actual geometry stride+0x68 × vertex count+0x8C. It creates buffers through `141E88B40` and associated resource views through `141E88CF0`. This source creates geometry buffers for this exact owner; no target-factory analogy is required.

`producer/001E92F0` is the concrete CPU interleaving writer. Under its lock it acquires the current engine recording context via `1419E76A0`, walks the owner's admitted geometry and real vertex declarations at model+0x2A8 (0x1C-byte declaration entries), and selects declaration semantics0,3,9 with index0. It allocates stride×vertex-count scratch. `update/001E7870` returns CPU owner+0x30; `001E7860` returns owner+0x38. The writer maps each vertex through `1401EE060`, copies the current three 4-byte components into the declared semantic0 offset, and writes the packed4-byte channel using `1401EE0C0` override or owner data. A further4-byte channel comes from `1401EE090`. Calling these position and packed normal is a strong interpretation of the layout and named family; the raw source observation is exact sizes, getters, mappings, semantic IDs and stores. The semantic9 channel's precise meaning is not established here.

It calls `1419E4ED0(context+0x25C8, current native buffer, 0, 0, scratch, 0, 0)`, releases scratch, returns/enqueues the current context through `1419EC890`, then atomically sets the CPU ready flag through `140B75260`. **Ready is not GPU completion or even a universal successful-update proof:** the final ready setter lies outside the non-null-context branch. Do not infer that every error/empty branch produced initialized GPU bytes.

For the selected draw, `patch/00B75270` requires a buffer array, nonzero ready and stream index0. It chooses the owner's actual buffer indexed by the current mesh's ushort+2, takes stride from the incoming current geometry, updates the context's current VB association, and calls `141E8DAF0` with offset0. This is the concrete join between the CPU-update resource owner and normal selected Flver binding, not a detached demonstration draw.

The related resource callback `patch/00B75350` chooses the corresponding ready view and calls the supplied callback. Its C prototype hides the view argument; use ASM before calling it. `patch-owner/01AC12B0`, identified by the RTTI-named ApplyStreamPatch functor, associates the supplied resource with current shader slots (including the animation stage slot0x1F arm) and marks descriptor ranges dirty. IA and shader-visible views are distinct associations of the same owner.

## 3. Native allocation, update and upload completion

The actual buffer creation chain is `native-update/01E88B40` → `completion/01E89A10` → `material/01E8B240` → `factory/01E97D50` → `selected/01E98000` → `allocation/01E928E0`. It validates size/stride/flags, resolves shared native service/device globals, constructs the native descriptor, aligns allocation size to256, and calls device **slot0xD8 CreateCommittedResource** (or an optional placed-resource arm, slot0xE8). The wrapper constructed by `factory/01EAB4F0` retains native resource+0x20, byte size+0x2C, flags+0x34 and descriptor storage+0x48. Initial-data upload exists as a separate factory branch; the patch's null initial data must not be described as executing that branch.

`update/019E4ED0` surrounds the ordinary update with native state transitions through `141E8EB10`, invokes `141E8D570`, and restores the prior state selected by `1419E5410`; a special-mode branch skips those transitions. `native-update/01E8D570` distinguishes buffers from textures. Its buffer arm selects the current context's upload allocator (+0x20 or +0x28), determines byte range, allocates mapped storage through `141E8F770`, copies actual current scratch bytes with `14251E710`, resolves upload offset/resource via `141EAC870/141EAC860`, and records **CopyBufferRegion, command-list slot0x78**. At `141E8D8EB`, ASM exposes destination native resource in RDX, destination offset R8, source upload resource R9 and source offset/size on stack. This is the CPU→native transfer, before selected IA binding of the retained destination resource.

`update/01E8F770` suballocates aligned blocks, obtaining more through `native-update/01EAC800` → `completion/01EB1620`. `main-draw/01EAC5C0` creates the upload owner's native buffer with heap type2/UPLOAD and state0xAC3/GENERIC_READ, maps it through resource slot0x40 with empty read range, and retains native resource+0x18 and CPU mapping+0x20. This is a concrete persistently mapped native arena, not a captured byte table.

Existing ER primary `evidence/I-0007/artifacts/producers/ER-271-F-01EA4C10.c/.asm.txt` executes resolved current lists (queue slot0x50), signals its actual fence/value (slot0x70), then transfers their upload blocks to `141EAC840`. ASM `141EA4EBF/141EA4EEF` retains the actual block in R9 despite a deficient C prototype. `native-update/01EAC840` attaches queue-class and fence value to the block. `01EAC850` reads that queue-class's fence through `completion/01EAB300` (**GetCompletedValue, fence slot0x40**) and returns a block to the reusable arena only when recorded value ≤ completed value; unfinished blocks remain deferred. This closes upload lifetime through native completion.

## 4. Current material/pose inputs become actual native CBVs

`factory/01AC1940` applies current per-instance scheduling/state gates, reads the owner's current matrix fields +0xE0…+0x118 into a local 4×3 arrangement, and passes current model+0x18, selected geometry/LOD, pose+0x158, stream patch+0x1D0, current instance handlers and draw information to `material/01AC1D30`. The latter performs matrix/pose calculations, visits current geometry/material associations and instantiates the RTTI-named **GXMaterialResourceCollector_Animation** at vtable142F21548. This proves an actual current animation/material preparation family, not all materials in ER.

It calls `completion/01A15E70` on the current material/program owner. That helper uses the current CPU parameter object at owner+0x168 or constructs a current merged object with active modifiers. `material/01B7DB80` calls collector virtual+0x18 with the parameter object's descriptor/resource association, **actual CPU pointer at +8 and size = count at +0x18 ×16**. Vtable slot0x18 is `factory/01ABFFF0`, which invokes `producer/01ACF120`, records the matching native resource and returned CPU-upload pointer in the current stage tables, and marks the binding dirty. The neighboring transiently recovered `141ABFF10` and `141AC0200` are actual RET no-ops; do not invent callbacks for those slots.

`01ACF120` requests mapped space through `producer/01E8EB70` from the current context's upload allocator and copies the current parameter bytes. `completion/01ACD380` later gathers both current resource references and corresponding transient CPU pointers. Report710 `prepare/01ACD170` category2 allocates the current descriptor table and calls `completion/01E9BE20`. When a transient CPU pointer exists, `material/01EAC880` translates that pointer into the upload resource's GPU virtual address plus its mapped offset; byte size is aligned256; device **slot0x88 CreateConstantBufferView** writes the real descriptor. Otherwise the resource's existing CBV is copied. ASM `141E9BED7` passes the actual current CPU pointer to address translation and `141E9BF00` is the native CBV call.

Report710 `data/01E8F3B0.asm.txt` binds the resulting GPU descriptor handle at the current root-table index (graphics slot0x100 or compute0xF8). Report710's current pipeline/descriptor preparation precedes the indexed draw. Thus current CPU material/pose-derived data, current resource associations, transient upload allocation, native descriptors and command binding all exist in the same renderer method. No semantic claim that a particular float is a camera or a particular texture is a face image follows merely from these buffer offsets.

## 5. Withdrawal, delayed resource destruction and frame order

`patch-owner/00B74E50` withdraws the owner's buffers/views/maps. Before dropping its native-buffer reference it calls `producer/01A973A0(resource,0)`. ASM retains resource+0x10 and tail-jumps to `141AF4380` using manager global+0x5B8, release-policy object143C26B80 and delay=argument+2. PE reads `retire-tag.json`/`retire-vtable.json` resolve this policy's virtual+8 to `frame-order/01A96F50`: decrement resource reference, invoke concrete destructor on last reference, then free wrapper memory.

`retirement/01AF4850` transfers incoming delayed buckets into the active list with counter+1. `01AF4580` decrements active counters, invokes the policy when counter<1 (with a per-call work budget), and frees consumed records. Frame beginning `frame-order/019E77F0` calls the transfer helper; frame ending `019E82C0` calls the release helper. The concrete native wrapper destructor `allocation/01EAB580` → `factory/01E97E30` releases descriptors, native COM resource and associated allocation ownership. This closes withdrawal to actual destruction, including deferred retention.

**It does not prove a per-resource fence check.** The delayed manager is CPU/frame-count based in these sources. Frame ending calls `frame-final/019EE770` before `01AF4580`; `frame-native/01AFC9A0` waits on GetCompletedValue for a selected frame-ring token, and `01AFC980` queries its completion. But selection depends on current frame-lag policy (+0xF1C, ring of6), and a diagnostic escape exists in the wait. The invariant relating the patch's delay2 to every resource's last use and every frame-policy configuration has not been established. Do not transfer “wait two frames” to DS3 as a proven GPU-safe rule. Explicit submission-token ownership in the integrated backend is a defensible DS3 design inference, not a claim that this ER manager implements precisely that abstraction.

Existing primary `ER evidence/I-0007/artifacts/records/ER-271-F-01AECB00.c` flushes accumulated lists before ordered callback records; it flushes residual lists at end. `retirement/019E85F0` finalizes the current ordered-record array and processes it via `presentation/01AECAE0` → `141AECB00`, then rotates CPU recording arrays. In the worker path `frame-native/01AF5060` publishes current ordered-record work to the renderer worker; `01AF5180` processes it through `retirement/019ECCA0` before invoking its pending presentation-like virtual callback. That processing inserts preparation/finalization callbacks `frame-order/019EEE20/019EEE90` into the same ordering.

Native presentation itself is concrete: `frame-order/019EC620` walks current presentation owners; `retirement/01AFCB60` passes current settings into `presentation/01E99800` → report710 `prepare/01E9F630`, which calls swap-chain Present slot0x40, signals its associated queue/fence on accepted result, and refreshes GetCurrentBackBufferIndex slot0x120 on success. **The worker's callback object's concrete registration as 1419EC620 is still missing.** `frame-refs.txt` and an all-decoded-instruction operand scan (`present-scan`) found only metadata references to that function, not a constructor/registration. Static temporal order and native presentation are established separately; a same-object end-to-end live draw/present claim would be fabricated. No ER live run was needed to invent or conceal that gap.

## 6. Coherent DS3 responsibility design informed by these observations

The following is an inference for the principal to validate against DS3 source, not transplanted ER layout/ABI and not implementation authorization for this worker.

1. **Start at actual current owners.** Preserve DS3's genuine model geometry, physical/FaceGen CPU producers, instance matrices, current view/LOD/material selection and real shader/texture inputs. Resource creation, CPU update, selected use and destruction form one lifecycle contract. Do not patch only the latest old-GPU allocator reached during loading; first enumerate that owner's complete lifecycle and all participating data families.
2. **One backend owns GPU consequences.** Current engine resource requests allocate through the existing startup DeviceQueues device; CPU updates obtain backend-owned upload storage and record native updates. Native resource/views remain associated with their genuine engine owner. Existing DS3 native model storage, upload facilities, descriptors and encoders should be reused after their direct contracts are checked. A D3D11-shaped stand-in or a generic adaptation/transport API is not the target.
3. **Selection consumes those same current associations.** Current selected mesh/instance/material preparation chooses original geometry or the appropriate current dynamic stream, resolves current material constants/textures, and records IA/root/pipeline/draw commands on the integrated context. Updating one buffer in a diagnostic path while selected draws resolve another identity would violate the recovered method. Required resources and complete current data must have explicit readiness semantics; ER's CPU flag alone is not that proof.
4. **Recording owns the used versions until completion.** Preserve ordering of upload copies, state transitions, descriptor writes, dependent draws and callbacks. In DS3, select a documented strategy for repeated updates while prior work is in flight: ordered updates to retained destination storage or immutable/versioned storage with retained references. Do not overwrite transient upload/descriptor bytes still used by the GPU. Withdrawal removes future engine selection; outstanding native uses retain their resources until their actual submission token completes.
5. **Frame and presentation complete the same ownership domain.** Existing startup queues/window/swap chain continue to own recording submission and presentation. Native completion controls reusable upload/descriptor/list storage and retired resources. Frame targets/settings are current engine inputs. No second device, independent host, virtual-file publication or captured-frame intermediary is required by the observed method.

This yields three useful responsibilities inside one backend: current resource ownership/update/retirement; current view/instance/material preparation and command recording; ordered submission/completion/presentation. They need direct contracts, not another adaptation layer. Their contracts must be designed together before implementation resumes. ER provides a concrete working reference for the split; DS3 determines the actual structures, calls, legal update timing and supported families.
