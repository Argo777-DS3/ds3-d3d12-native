## 1. What the pass looks for

RESULT §4's limits were: chains split by a jump (TRTF's decay branch), integer counters, packed (vector) updates. The tool adds:

| Kind | Rule | Rows | Functions |
|---|---|---|---|

| INT_COUNTER | an integer field stepped by a constant per call (`INC`/`DEC`/`ADD`/`SUB` imm on the field, or through a register loaded from and stored back to it), with the immediate it is compared with next | 2,156 (11 compared with an immediate) | 1,463 |

Check: the SPLIT pass finds a second store in the locomotion function `1405C72B0` (LTF's site, §1): `[RBX+0x25C] *= 1.2`
behind a branch (`1405C7421`), a new site in a known function. It does **not** find TRTF's decay branch in `1405E6580` (the
`retention·state` multiply sits behind a jump the pass does not walk: a chain joined by an unconditional jump, or its operand a
register loaded earlier). So split chains are still only partly covered (§3).

## 3. What this adds for the unlock workstream

1. **One new site to fix with LTF's**: `1405C72B0`'s second branch (`+0x25C *= 1.2`).
2. **One to read at runtime**: `14087E8A0`'s multiplier `+0x1A4C` (rebuilt each frame or not).
3. **Two frame-count cadences**: the 30-frame cycle of `1406830F0` and the 4-frame delay of `14072FEC0`; time-based at any
   rate only if their subsystem needs it (name them first).
4. **No packed recurrence** of game state was found: the vector updates the pass sees are math, not per-frame state.
5. **Still uncovered**: split chains joined by an unconditional jump or fed by a register loaded before the branch (TRTF's
   decay branch is one), and integer frame counts compared with another field. The runtime counter I-0112 §5.1 proposes (call
   frequency per site) is the next tool; a decompiler-based pass (p-code data flow per function, the self-recurrence through
   any path) would close the static side, at the cost of decompiling the candidate functions (about 250 with §1's and §4's).
